# Runtime (Backend) Integration Guide

A runtime is an Agent CLI installed on the local machine (`Backend` in the code). It is a **global resource**: the registry lives in SQLite and is shared by all projects; global role templates and project roles are each bound to a specific runtime and model, which are used directly at execution time with no runtime routing. A new project copies the global role templates as they exist at that moment, with the first entry as the default orchestrator; after that, the templates and the project roles are maintained independently.

This document explains which tools are supported, what technology is used to integrate them, how they are detected and upgraded, where model lists come from, and how to integrate a new tool. The providers and the unified management layer under `missioncrew/runtime/` are the source of truth for every fact here.

Project roles are bound to a fixed runtime/model, and tasks no longer go through stage routing.

## Unified Runtime Abstraction Boundary

Business modules depend only on `missioncrew.runtime.runtime_manager` and the unified domain objects; they may not import `runtime.adapters`, call `get_adapter()`, or branch on raw executor constants such as `ACP_SERVE_COMMANDS`. The commands, protocols, and process details of CLI, ACP, and Mock are encapsulated inside the runtime package by `RuntimeProvider` implementations.

The unified control plane provides the following operations:

- `start(ExecutionConfig) -> RunResult`: start one runtime execution; process events and the final result use a unified format.
- `stop(Backend, session_key="") -> int`: stop the specified runtime's active CLI processes, one-off ACP executions, or long-lived sessions.
- `interrupt(Backend, session_key="") -> int`: native providers interrupt the current turn but keep the session/thread so the next turn can continue it; runtimes that do not support this return 0.
- `supports_session()` / `capabilities()`: query the actual session reuse and lifecycle capabilities, so the chat layer no longer guesses the runtime type.
- The Claude/Codex native providers also declare `structured_events`, `user_interaction`, `permission_control`, and `interrupt`; pi declares only `structured_events` and `interrupt` (pi RPC has no channel for passing permission requests or questions back). The frontend presents actions based only on capabilities and never checks for the Claude/Codex names.
- `list_models()`, `effort_options()`: unified model and reasoning-effort management.
- `account_usage()`: read the limit windows of the account logged in on this machine; providers return only a unified snapshot and do not expose credentials or raw upstream responses.
- `detect_report()`, `detect_backends()`, `update()`, `refresh_installation()`: unified discovery, registration, upgrade, and version probing.
- `register(adapter, provider)`: register an implementation for a new runtime or plugin without modifying the chat, task, API, or CLI call chains.

If a `start()` provider internally serializes the same session with a session lock, it must call `ExecutionConfig.cancellation_requested()` after acquiring that lock and before starting a new turn or child process. A channel stop can happen after the call has entered the provider but before it actually acquires the session lock; checking only at the `RuntimeManager.start()` entry point would let a queued turn start after the current process has been terminated. The built-in Claude, Codex, ACP, print-mode, and Mock providers all follow this contract.

`ExecutionConfig.runtime_policy` is the runtime-agnostic execution policy and contains `readable_paths`, `writable_paths`, `skill_paths`, and `RuntimePermissions`. Permissions are currently expressed uniformly as an approval mode `auto|prompt|deny`, a file system mode `read-only|workspace-write|full-access`, and a network mode `inherit|allow|deny`. The runtime manager generates `MISSIONCREW_READABLE_DIRS`, `MISSIONCREW_WRITABLE_DIRS`, `MISSIONCREW_SKILL_DIRS`, and `MISSIONCREW_RUNTIME_PERMISSIONS`, and providers then translate the policies they can support into command arguments or ACP permission responses. `allowed_dirs` exists only as a compatibility field for the old construction entry point.

Summaries of project skills and decisions about their applicability still belong to the project context; the runtime layer is responsible for injecting the selected skill directories into all runtimes as a unified policy. Write operations that chat roles perform on MissionCrew likewise never go into the raw executors: an Agent Tool URL and a per-run capability file at a stable path are injected uniformly, and Claude, Codex, ACP, and print mode all call the same HTTP/CLI contract. Delete actions go into the project's unified recycle bin; the orchestrator manages recycled items through `recycle.list`, `recycle.restore`, and `recycle.purge`, and runtimes never read or write its internal storage directly. This keeps project semantics out of the raw executors and keeps runtime differences from leaking back into the main program. For the specific actions, permissions, and error structure, see [MissionCrew Agent Tool API](agent-tool-api.md).

## Live Run Status

The system polls `GET /api/runtime/status` every 10 seconds and caches one shared copy of the global status. The "运行状态" (Run Status) indicator in the lower-left corner shows the number of instances currently executing; the role buttons above the chat input mark, by `project_id + role_id`, whether the corresponding role is currently running; entering the global run status page or clicking "立即刷新" (Refresh Now) sends an additional immediate request. The page does not read any runtime's internal structures; instead, `RuntimeManager.status()` aggregates the unified `RuntimeInstance` snapshots returned by each `RuntimeProvider.instances()`, so a new provider only needs to implement instance enumeration, with no page branches to modify.

Snapshots distinguish two lifecycles:

- `persistent`: Claude stream-json, Codex app-server, or ACP stdio sessions that stay resident in the server process and can be reused. They show `running` while running, `idle` when the turn has ended but the process is still alive, and `disconnected` when the process exited abnormally but the instance record still exists. The periodic reaper thread of `RuntimeManager` scans every 60 seconds and closes long-lived sessions that have been idle for more than 30 minutes; sessions that still have an active turn, a wake turn, background commands, or unfinished background agents are not reclaimed. Native session/thread ids are persisted, so a reclaimed session continues in the next turn with a new process through its own resume mechanism.
- `one_shot`: print-mode calls and ACP calls without a session key. They show `running` while the child process exists and are removed from the status page as soon as it exits.

Every instance uniformly provides the backend, adapter, transport, PID, session key, native session/thread id, project, role, model, working directory, start time, and last activity time. Print mode reports through the active process registry; ACP reports both the long-lived pool and one-off clients; the Claude/Codex native providers report their session objects directly. The runtime overview on the page always lists every registered runtime; even when there is no process, it explicitly shows the runtime as not running or disabled.

### Account Usage and Limits

The "账户用量" (Account Usage) section at the top of the run status page comes from `GET /api/runtime/usage` and currently supports Codex, Claude, Kimi, Grok, and Antigravity. "Usage" here means the subscription or credit quota windows of the account currently logged in to the local CLI; it is neither MissionCrew's own estimate of call cost nor the call history in SQLite shown further down. Every provider converts its raw result into a `RuntimeUsageSnapshot`: each window contains only a name, used percentage, remaining percentage, window duration, and reset time, optionally with non-sensitive metrics such as the plan name, balance, and concurrency limit. The page uses the body of a progress bar to show the share of quota used and a triangle below it to show time progress, computed from the window duration and reset time; supplementary metrics appear right after the runtime title, and hovering over a window shows the full quota, cycle progress, and reset time.

`RuntimeManager.account_usage()` probes the runtimes that support this capability in parallel (one thread per backend, so the total time equals that of the slowest one) and caches results in the server per backend for 60 seconds. While a probe for a runtime is in progress, concurrent requests that arrive (re-entering the page, several clients opening it at once, task-completion triggers) share that single result instead of launching a second process that slows both down and then overwrites the cache in completion order. Entering the run status page only reads the in-server cache (re-probing only when it has expired); only clicking "立即刷新" (Refresh Now) forces a re-probe of all runtimes. When a runtime task ends, if a role with usage linkage enabled is using that runtime, only that one runtime is re-probed and no other CLIs are launched. While the page stays open, the regular 10-second polling updates only the runtime status and call history; it does not request account usage, and there is no periodic account probing thread. A task-completion event wakes only one refresh, and events completing in quick succession are merged; when there are no linked roles, the event is simply ignored. A failed probe only makes the corresponding card show "需要登录" (login required) or "暂不可用" (temporarily unavailable) and does not affect the run status, chat execution, or the limits of other runtimes. Limit snapshots are kept only in memory and never written to SQLite; the API does not return access tokens, refresh tokens, user identifiers, credential paths, or upstream error bodies.

Usage linkage is the role's own `usage_linkage_enabled` switch, off by default; it is not a runtime-level or system-level switch. Only roles that explicitly turn it on are disabled automatically when an applicable window reaches 100%; roles under the same runtime that use a third-party LLM API, or that should not follow the current account's quota, keep it off and are not affected by other roles. Global role templates also store this field; once copied into a new project it becomes the initial value for each project role, which can still be changed individually afterward.

The automatic-disable attribution and reset time are stored separately in SQLite, and roles that were already disabled manually are not taken over by the linkage. When a known `resets_at` arrives, the background only performs a local timed recovery without probing the account; windows without a reset time recover when the next task completion or page refresh detects that quota is available. Turning off linkage for a role immediately re-enables that role if it is still disabled by this mechanism; rebinding the runtime or model likewise clears the automatic-disable attribution of the old execution combination. Manually enabling or disabling a role clears the old automatic attribution, so the timer will not mistakenly re-enable a role that was later disabled manually.

Kimi's `/usages` and OAuth protocol come from the managed-provider implementation bundled with the CLI. Grok's billing path is used internally by the Grok CLI and is not a public ACP v1 method; if upstream changes the path or response structure, the corresponding card degrades safely and the chat runtime keeps working.

Credential reading follows least privilege: it reads only the CLI login files of the current service user and puts the token only in the `Authorization` request header for the target domain; tokens are never written to logs, included in exception messages, returned to the frontend, or persisted to the database. Kimi OAuth refresh is the only path that updates a credential file directly, and that update uses a temporary file in the same directory, `fsync`, atomic replacement, and `0600` permissions; Grok refresh is delegated entirely to `grok models`. If the credentials do not exist, the JSON is corrupt, or the permissions are broader than `0600`, MissionCrew does not use them and reports that login is required.

The "使用历史" (Usage History) section further down the page comes from a separate `GET /api/runtime/history` and records each `RuntimeManager.start()` call rather than process instance lifecycles. `RuntimeProvider.execution_info()` declares the `persistent` / `one_shot` form and transport of that call; the unified manager writes `running` before calling the provider and, after it returns, updates the record to `succeeded` or `failed`, or records it as `interrupted` when the user has already stopped this turn. Records include the runtime, project, role, session key, model, effort, working directory, start and end times, and duration, and are stored in the platform SQLite, so they survive service restarts.

`ExecutionConfig`, `RuntimeInstance`, and `runtime_usage` all carry both `project_id` and `role_id`. The global runtime overview therefore aggregates the project and role that current instances belong to, and the instance and history tables show both fields directly; for non-project calls both may be empty.

## Integration Technology

### Per-Runtime Session Reuse Matrix

Within one context cycle, a chat session is keyed by `channel::role`, but each runtime's native interface is different. The channel stop button in the chat area atomically changes all `queued`, `running`, and `waiting_user` runs of the channel to `stopped`; it first cancels pending interactions, then calls `stop` uniformly on the runtimes of the active runs and of the sessions saved for the channel, terminating the native processes and their background child processes. Stopping does not delete the native session/thread IDs persisted in `chat_sessions`, so the next turn creates a new runtime process and tries to resume the native context. The native ID is written to the database at the moment the prompt is handed to the runtime (Claude at `system/init`, Codex at `thread/start`, ACP before `session/prompt` is sent, pi after `prompt` is sent), not when the turn ends: so when the first turn of a session is stopped manually mid-turn, the next turn still continues the work already done under the same native ID (an incremental turn) instead of degrading into a new session because persistence only happened at turn end. Even when the database has no active run, the stop API still cleans up orphan processes belonging to the sessions saved for the channel. The run thread checks for a terminal state before starting, on output events, on failure publishing, on orchestrator actions, and at the final reply boundary, so late results after a stop cannot reopen the run or trigger follow-up agents. Partial changes already written to disk are kept; there is no implicit rollback.

After the user clicks "清除上下文" (Clear Context), the platform first confirms that no agent is running in the channel, then stops the persistent instances of each role in the channel, deletes `chat_sessions`, writes a visible `context_boundary` separator message, and switches subsequent keys to `channel::role::context-<marker-id>`; as a result, even CLIs with fixed session ids or stable directories will not reconnect to the context from before the clear. The recent conversation only selects records after the separator message; old messages and the full history file are kept for humans to view or for agents to read on demand. "Subsequent turns" in the table below all send only the latest MissionCrew shared context and the current trigger message, without replaying the recent conversation again; the resume input containing the recent conversation JSON is sent only when a new session is created, the original session cannot be resumed, or there is no reliable native interface.

| Runtime / adapter | How the first turn is created | How subsequent turns reuse it | Session ID source and process lifecycle |
|---|---|---|---|
| Claude / `claude_code` | Starts a bidirectional stream-json process and saves the native session id from `system/init` | While the service is alive, writes the next user message into the same process; after the process or service restarts, resumes with `--resume <id>` | ID returned by the runtime; one long-lived process per `channel::role`, reclaimed after 30 minutes idle (not reclaimed while there are background commands or background agents). Changes to the model, effort, directories, or environment restart the process but resume the same session |
| Codex / `codex` | Starts `codex app-server` and calls `initialize → thread/start` | Calls `turn/start` in the same process on the same thread; after the process or service restarts, calls `thread/resume` first | Thread id returned by the app-server; one long-lived process per `channel::role`, reclaimed after 30 minutes idle. A failed resume explicitly ends the current turn; no new thread is silently created |
| Grok / `grok_build` | Creates a session with `session/new` and keeps `grok agent stdio` in the server process | Continues turns directly within the same server process; after a restart, resumes through `session/load` with `_meta.noReplay=true` | ACP session id; reused long-lived per channel × role, reclaimed after 30 minutes idle; resumed history does not enter the current run |
| OpenCode / `opencode` | Starts with `--format json` and captures the session id from the JSON events | A new process uses `--session <id>` and keeps JSON output | ID returned by the runtime; one CLI process per turn. If no ID was captured, the next turn falls back to the resume input |
| GitHub Copilot / `copilot` | Starts a `copilot --acp` serve process and calls `session/new` | Reused long-lived while the service is alive; after a restart, resumed with `session/load` (history is replayed; the protocol layer calls begin_turn only after load, so the replay does not enter this turn's reply) | ID returned by ACP; one long-lived process per `channel::role`, reclaimed after 30 minutes idle |

| Pi / `pi` | Starts a long-lived `pi --mode rpc` process and, after the first turn, saves the session file path from `get_state` | While the service is alive, sends the next `prompt` directly to the same process; after the process or service restarts, resumes with `--session <file>` | SQLite stores the absolute path of the session JSONL (under `MC_HOME/pi/sessions/`); one long-lived process per `channel::role`, reclaimed after 30 minutes idle |
| Kimi / `kimi` | Starts an ACP serve process and calls `session/new` | While the service is alive, calls `session/prompt` directly in the same process with the same `sessionId` (model and effort are aligned within the session each turn through `session/set_model`/`session/set_config_option`, so changing the effort level does not restart the process); after MissionCrew restarts, calls `session/load` only when the runtime declares `loadSession` | ID returned by ACP; one long-lived process per `channel::role`, reclaimed after 30 minutes idle |
| Kiro / `kiro` | Same as Kimi: ACP `session/new` | Same as Kimi: long-lived reuse; after a restart, capability-gated `session/load` | ID returned by ACP; one long-lived process per `channel::role`, reclaimed after 30 minutes idle |
| Qoder / `qoder` | Same as Kimi: ACP `session/new` | Same as Kimi: long-lived reuse; after a restart, capability-gated `session/load` | ID returned by ACP; one long-lived process per `channel::role`, reclaimed after 30 minutes idle |
| Trae / `trae` | Same as Kimi: ACP `session/new` | Same as Kimi: long-lived reuse; after a restart, capability-gated `session/load` | ID returned by ACP; one long-lived process per `channel::role`, reclaimed after 30 minutes idle |
| Mock / `mock` | Uses `mock:<channel::role>` as a deterministic session ID | Reuses that ID within the same session lock | No external process; for tests and demos only |

Session metadata is stored in the SQLite table `chat_sessions`: besides the native ID, it records the backend id, adapter, resolved workdir, and the version of the shared context last received successfully. A session is resumed only when the backend, adapter, and workdir are all compatible; it is cleaned up when the role, channel, or backend is deleted. Changes to project settings inject the complete new version of the shared context into the original session on the next turn; changes to Claude's model, effort, directories, or process environment restart the OS process but still resume the same session with the native id. If Claude/Codex explicitly reports that the session/thread does not exist or is invalid, the current turn fails and the old record is deleted; a new session is never silently created within the same turn. Only when the user explicitly retries next time is a new session built with the resume input.

Runtime start commands are maintained by the provider and cannot be overridden through Backend data. To add or adjust a print-mode runtime, declare the `command` template, `session_id` (`fixed`/`captured`), and the `session_args` hook in the `CliSpec` in `runtime/clis/<tool>.py` and append it to `clis.SPECS`; `DEFAULT_COMMANDS` and the session strategy sets are aggregated automatically from the declarations. Also add tests for the first turn, continuation, and missing IDs. ACP serve commands are likewise declared in `CliSpec.acp_serve` and aggregated into `ACP_SERVE_COMMANDS`.

### Claude Bidirectional stream-json

The default Claude provider launches the official `claude` with `--input-format stream-json`, `--output-format stream-json`, `--include-partial-messages`, and `--permission-prompt-tool stdio` together. stdin stays open for the entire lifetime of the process, and a structured user message is sent each turn; the system, assistant, user, stream event, and result messages on stdout are converted into status, thinking, tool, tool result, text, and final result events.

Claude's native background agents are not disabled. The provider consumes the stream-json `task_started`, `task_progress`, `task_updated`, and `task_notification` messages directly, tracking background subagents within the same turn by `task_type=local_agent|remote_agent` and `task_id`; `task_updated` only updates the task record, while `task_notification` is the terminal boundary of a result the parent agent can consume. If agents are still running when a top-level `result` arrives, that result is written to the process stream only as an intermediate result; MissionCrew keeps the chat run, stdout reader, permission callback, and session lock valid until all background agents have terminated and Claude then emits a new top-level `result`, and only then publishes the final channel reply. The asynchronous launch text returned by the `Agent|Task` tool is used only for compatibility with older CLIs that lack `task_started` and must not serve as the main completion signal. The start, progress, waiting, and completion states of background agents are shown in the chat run card as structured `backend_agent` events.

Background commands (Bash `run_in_background`, i.e. non-`_agent` tasks such as `task_type=local_bash`) have the opposite semantics from background agents: they do not block the top-level `result`, the chat run ends normally, and subsequent messages are processed as usual; the task list survives across turns and counts toward the instance snapshot, and the status page shows "N 个后台命令" (N background commands) on the instance row, warning that reclaiming, stopping, or restarting the instance also terminates these commands. When a task ends, the Claude CLI spontaneously starts a reporting turn with no user input once the session is idle; the wake-up is handed to ChatEngine through the two-stage callback registered with `RuntimeManager.set_wake_handler(handler, begin=…)`: at the start of the turn (when `init`/`assistant`/`stream_event` is received while idle), the provider **synchronously** calls `begin` (session_key, role, triggering task), and ChatEngine immediately materializes a run anchored on a platform message ("后台命令已结束", background command finished), issues an Agent Tool token bound to that run, and returns a live event receiver, so process events within the turn go straight to the run (events already buffered during `begin` are replayed first, in order); after the turn's `result` arrives, the final output is handed together with the `run_id` to `handler` to finish up (publish the report or record the failure, and revoke the token). The token must be issued at the start of the turn: when a regular run ends, `deactivate_run_token` has already revoked and deleted the token file at the stable path, and the wake turn executes in the CLI process before the platform knows about it, so if the run were only materialized after the turn ends, every platform write operation within the turn (publishing documents, updating tasks) would fail for lack of a token. When `begin` is absent, returns None (the session does not exist, the channel is stopping, or token issuance failed), or raises an exception, the provider falls back to the old path: events are buffered, and after the turn ends they are handed to `handler` as a whole, which creates a new run and replays them. A wake turn that has been materialized as a run is always finished up whether or not it produced output; if the process is shut down midway (stop, restart), `close()` notifies the platform with a failure payload, so the run does not hang in running. An explicit channel run waits for an in-progress wake turn to complete before sending user input, and registers its active sink under the same condition lock, preventing the wake sink from swallowing the new run's events or final `result`. Dispatch semantics are inherited from **the turn that started the background task**: when the task is registered, the trigger message of that turn (`ExecutionConfig.trigger_message_id`) is recorded, and at wake-up, if that message was a human directly naming this role, the report is attached back to the original human message and not handed back to the orchestrator (consistent with regular replies to direct mentions); otherwise, results from non-orchestrator roles are automatically handed back to the orchestrator for acceptance. If the session record does not exist, the channel has been archived, or the role is disabled, the wake-up is silently discarded. The CLI queues each `task_notification` and, between turns, starts **one self-wake turn for each** in order (two notifications arriving at the same time also produce two turns, measured on 2.1.261); a notification that arrives during a turn which then makes another model call is fed to the model in place with that call and does not trigger a separate wake-up. The provider maintains its pending-wake queue by the same rules: a notification is enqueued on arrival together with the turn it arrived in; if that turn then receives a `user` message (meaning it will call the model again), the entries enqueued within this turn are removed; when a wake turn starts, it takes only the first entry of the queue as its task. This way the second wake-up of the same batch still carries its own `origin_trigger` and does not degrade into "unknown origin, hand back to the orchestrator" because the first wake-up took all the reasons. A self-wake turn has no corresponding run, so tool approval follows the policy of the session's most recent turn: `auto` allows (approval events are written into the wake buffer and replayed with the report), `prompt` is explicitly denied because there is no interactive run, and question tools are denied as well; otherwise the agent in the wake-up could not even read the background output and could only post an empty report. A late bare `result` (with no init/assistant before it) is not wrapped into a wake report. After a process is killed with background commands still unfinished (stop, service restart), on the next `--resume` startup the CLI itself inserts a `task_notification` for that task (status=stopped, "No completion record was found…") before the first `init`, immediately followed by a pair of empty `init`/`result` messages that do not call the model (`num_turns=0`), and only then processes the user message from stdin (measured on 2.1.258, regardless of when the message is written); the provider counts notifications that arrive before the first init as replay, and the subsequent successful result with `num_turns=0` is not treated as the end of this turn (it is also skipped when this turn has had no model activity yet; a result after an interrupt is always accepted), and both are written to the process stream as status events. Otherwise the turn would be judged as "exited normally with no output", and the model's real work that follows would land outside the run: tool permissions would be denied, and the final text would be treated as a self-wake report and opened as a new root post. Remote long-running tasks (such as an ssh deployment) can be tracked with a background ssh, and the ssh exit triggers an automatic report.

`can_use_tool` control requests are not decided by the Claude terminal itself but handed to MissionCrew. `AskUserQuestion`, `ask_user_question`, and `request_user_input` generate chat interaction cards; after the user answers, the provider writes the answers back to the original control request and the same turn continues. File writes and network tools first go through the hard checks of the unified policy and then into `auto|prompt|deny` approval. Claude's OS-level Bash sandbox is off by default: it puts Bash into an isolated network namespace where host loopback and private network ranges are all unreachable (the `NO_PROXY` injected by the sandbox also excludes them) and all domains are denied by default, which is too restrictive for purely local collaboration; the platform's other ACP yolo-style runtimes have no OS sandbox to begin with, codex also has an approval-escalation escape hatch, and the file write boundary is still enforced by the application-layer hard checks of the unified policy. When strong isolation is needed, set `MISSIONCREW_CLAUDE_SANDBOX=on` before starting `mc serve`: in non-`full-access` modes the sandbox is enabled through a temporary `--settings` and the unsandboxed escape hatch is forcibly disabled; if the sandbox is unavailable, execution fails instead of degrading. When it is enabled, `sandbox.network.allowedDomains` has no effect on loopback/private addresses (in testing, connections were still refused after allowing `127.0.0.1`), so `--settings` uses `sandbox.excludedCommands` to exclude the Agent Tool CLI (both invocation forms, `missioncrew-tool` and `python -m missioncrew.agent_tool`) from the sandbox: the command still goes through platform `can_use_tool` approval first and, once approved, runs on the host side, so it can reach the control plane at `127.0.0.1:8321`; the cost is that a compound command whose body contains that fragment also leaves the sandbox as a whole, which is backstopped by the approval layer and the least privilege of the role token. When the user stops execution, the corresponding Claude runtime process group and its background commands are closed directly; the saved native session ID can still be used by a new process to resume in the next turn.

### Codex app-server

The default Codex provider no longer runs `codex exec`; instead it starts the official `codex app-server` for each `channel::role` and uses a bidirectional JSONL protocol that omits the `jsonrpc` field. The connection first completes `initialize/initialized`, then calls `thread/start|thread/resume` and `turn/start`; agent message delta, reasoning delta, command, file change, plan, usage, and turn completion notifications are each mapped to chat process events.

Each turn passes `cwd`, `model`, `effort`, `runtimeWorkspaceRoots`, `approvalPolicy`, and `sandboxPolicy` in structured form. The `writableRoots` of `workspaceWrite` come from the unified `RuntimePolicy.writable_paths`; network access is allowed by default (the Agent Tool's loopback API and git operations both depend on the network, and disabling it would only turn every access into a sandbox failure plus an approval-escalation retry) and is turned off only when `RuntimePermissions.network=deny`. During the manager's `_prepare` stage, for `workspace-write` mode the unified policy adds the system temporary directories (`/tmp` and the like, to rescue toolchains that use them implicitly) and the runtime tool's own directories (the config/skill/memory locations declared in `CliSpec.private_dirs`, such as `~/.codex` and `~/.claude`) to the writable roots; `read-only` and `full-access` are not rewritten. The tool's own directories also enter the authorized directory list of the chat context through `runtime_manager.private_dirs`. The model catalog calls the app-server's `model/list` directly and falls back to the old CLI discovery path only on failure.

### Antigravity headless stream-json

Uses the official `agy` CLI; log in interactively once first. `runtime/antigravity.py` handles launching each turn, parsing `init` / `step_update` / `result`, and cleaning up the process group; the declaration module only handles detection, `agy models`, and `agy update`. The model, effort, and extra authorized directories are passed with `--model`, `--effort`, and repeated `--add-dir` respectively. Tool events and replies go straight into the unified event stream; `result.usage` is the session's cumulative total and maps to `usage/v1.total`, while this turn's `turn` is summed from the usage of each completed step. `result.status` / `result.error` are likewise taken from the session's stored state rather than from this turn: a continued session brings back, unchanged, the `ERROR` and error text left by a previous failed turn, and a successful turn does not clear them (measured on agy 1.2.4; this once caused a single rate-limit error to be reposted into every later turn and swallowed the normal replies). Therefore whether this turn succeeded depends only on the CLI's signals for this turn: an `error:` line on stderr, a non-zero exit code, a missing `result`, or an empty `response`; `result.error` is used as the reason only when the turn is judged to have failed.

`approval=auto` uses `--dangerously-skip-permissions`; `workspace-write` also enables the CLI's native `--sandbox` and adds the extra directories to the workspace; `full-access` explicitly turns the sandbox off. The actual boundary still depends on Antigravity's local permission configuration. The CLI has no per-tool approval response protocol, and `--mode plan` only adds planning instructions without guaranteeing read-only behavior, so `prompt` / `deny` approval, the `read-only` file system, and `network=deny` raise an error before launch instead of running in a degraded mode; the capability declaration offers neither interactive approval nor user input.

Success requires all of the following: a process exit code of 0, `result.status=SUCCESS`, a non-empty reply, and no denied actions. A missing terminal state, an error status, `denied_actions`, or a print timeout notice on stderr all count as failure, even if the CLI marks part of the output as successful. `--print-timeout 0s` returns immediately rather than disabling the timeout; when the platform has no deadline, it passes a value close to the Go duration upper limit and lets the stop operation manage the process, and with an explicit timeout it passes this turn's deadline duration. Stopping cleans up the entire process group and keeps the conversation ID already saved at init; no post-turn background processes are kept.

For the protocol, see the [Antigravity headless documentation](https://antigravity.google/docs/cli/headless/); verified locally with CLI 1.2.4.

### pi RPC and Raw API Integration

pi is used to turn **raw OpenAI / Anthropic-compatible APIs** into collaborative agents: the platform does not rewrite the agent loop but reuses pi's tool execution and session management directly. Integration uses the RPC mode that pi officially designed for cross-language hosts (`pi --mode rpc`), with line-delimited JSON: the client sends `{"type": <command>, "id": ...}`, the process replies with `{"type": "response"}`, and the turn's progress streams out as events such as `message_update` (text/thinking delta), `tool_execution_start/end`, `message_end`, `compaction_start/end`, `auto_retry_start`, and `agent_end`, each mapped to chat process events (`agent_start` produces no process event). Note that `agent_end` is not a reliable end of turn: on transient errors pi sends `auto_retry_start` right after `agent_end` and starts another round, so the provider decides the end of the turn by a short quiet period (no retry event within 1s).

Isolation conventions:

- **Vendored binary**: pi is installed in `MC_HOME/pi/vendor` (`npm install --prefix`); detection recognizes only this installation and does not probe the system PATH, and upgrades also write only to the vendor directory, never with `-g`;
- **Self-contained configuration**: at launch `PI_CODING_AGENT_DIR=MC_HOME/pi/agent` is injected, so models.json and skin/theme configuration all live in the platform data directory and `~/.pi` is never read or written; session JSONL files always go to `MC_HOME/pi/sessions` (`--session-dir`), and extension discovery is disabled (`--no-extensions`);
- **Raw API configuration**: `MC_HOME/pi/agent/models.json` declares providers in pi's native format (`baseUrl` + `api` (openai-completions/openai-responses/anthropic-messages/google-generative-ai) + `apiKey` (a literal or `$ENV_VAR`) + a model list); the execution unit is `provider/model`, and the model catalog comes from the same file. This file is the storage implementation of the "Custom Model Integration" capability described below and is not exposed to users directly.

Each turn: while the process is alive, `prompt` is sent directly (differences in model and thinking level are aligned within the live process through `set_model`/`set_thinking_level`, without restarting the process); effort maps to pi's thinking level (off~xhigh). Interrupting sends `abort`. After the turn ends, the session file path is read from `get_state` and persisted, and after a restart the session is resumed with `--session <file>`. pi has no background task/self-wake protocol, so its long-task semantics are the same as codex (waiting within the turn).

### Chat Interaction and MissionCrew Permission Takeover

Native user-input/permission requests are persisted as separate JSON events, and the chat run status switches to `waiting_user`. The user's answer is passed back by run id and a random request id; the raw answer exists only in the in-memory pending request and is not written to run events, so secret input or credentials never enter the logs. Once answered, the native request receives a response and the run returns to `running`.

Meaning of the unified approval modes:

- `auto`: MissionCrew YOLO. The runtime still stays in request-approval mode, and the platform approves each request automatically and saves an audit event without sensitive answers; Claude `bypassPermissions` or Codex `danger-full-access + never` are not used to bypass the platform.
- `prompt`: shows a permission card supporting approve once, deny, or cancel; when the runtime provides persistable permission suggestions, an extra "本会话批准" (Approve for This Session) option is shown, and Claude passes the native `permission_suggestions` back unchanged as session-scoped `updatedPermissions`.
- `deny`: the platform denies the request; Codex also uses `approvalPolicy=never` with the configured sandbox, so out-of-bounds operations that cannot be approved fail directly.

Automatic approval and the sandbox are two separate layers: approving a request does not mean ignoring the file system boundary. For `item/permissions/requestApproval` requests for extra directories or network access, Codex passes back the exact permission profile requested; Claude uses `updatedInput` to continue the approved tool call. Every interaction has the same deadline as the current turn, and a timeout is treated as a cancel.

Codex's workspace-write sandbox also mounts `.git`, `.agents`, and `.codex` under each writable root, as well as the main repository's `.git/worktrees/<name>` resolved from a worktree, as read-only, so git write operations and in-repo skill edits fail inside the sandbox with `Read-only file system`. The platform does not rewrite these roots: listing subdirectories of `.git` as extra writable roots makes the sandbox fail to start because it cannot create placeholder mount points, and opening up all of `.git` would expose hooks/config. Instead, the "Must Follow" section of the shared context and section 3 of the manual guide the agent, when such a failure occurs on a listed path, to request escalation and rerun rather than concluding that the environment is read-only and giving up.

Every runtime process event in the chat is rendered as a collapsible item, including input, thinking, commands, tool results, logs, usage, and interaction requests. Each run card expands one item at a time: on first load only the latest event is expanded; when a new event id arrives, the previous item collapses automatically and the new one expands; when the user manually expands any older item, the other items in the same card collapse. Streaming content appended to the same event is not mistaken for a new item. Plain text events are physically split into 8000-character segments in SQLite, and the read API reassembles adjacent segments of the same kind before display, so long diffs, paths, or log lines do not form new collapsible items starting in the middle of arbitrary characters; structured JSON events such as permissions, questions, usage, and backend agents are always kept one by one.

Usage events are unified into the `usage/v1` structure at the runtime layer: each provider uses its own field table to map what is reported into two sections, `turn` (this turn) and `total` (cumulative), each with the fixed fields `input`/`cache_read`/`cache_write`/`output`/`reasoning`/`total`, optionally with `context_window`, `context_used` (the current context occupancy; when a turn makes several model requests the turn total is far larger than what is actually in context, so the frontend context bar prefers this field), `cost_usd`, `tool_uses`, and `duration_ms`, while `raw` keeps the reported content unchanged. Codex takes it from `thread/tokenUsage/updated` (last→turn, total→total, modelContextWindow→context_window), pi from the assistant usage in `message_end` (including cost.total), the main Claude turn from `result` (Anthropic fields plus total_cost_usd/duration_ms; raw keeps only usage-related keys), and the total_tokens/tool_uses/duration_ms of Claude background agents are carried with `backend_agent` events; for ACP tools the protocol layer emits one event at the end of the turn, taking the standard fields from the `usage` of the `session/prompt` response (this turn; continuation prompts within the same turn are added up field by field) and the latest `usage_update` (used→context_used, size→context_window, a cumulative session cost in USD→cost_usd), while private vendor extensions only fill gaps through the `parse_prompt_usage` hook: grok's `_meta.usage` (this turn's usage, `costUsdTicks` converted at 10¹⁰ ticks per USD, `apiDurationMs`; `_meta.totalTokens` is the context occupancy) and trae's `_meta._trae/tokenUsage.sessionTotal` (cumulative); kimi reports no usage, so no event is emitted. The frontend lays out only this one structure (one line per section, k/M abbreviation, a context usage bar, and the raw report collapsed); historical events without a `schema` marker are shown as raw JSON. A new runtime only needs to provide a field table inside its provider.

### Print-Mode CLI (`CliAdapter`)

Tools without a native bidirectional provider still use print mode: one execution = one child process; arguments are rendered from the built-in command template, the process is started in the channel's working directory, stdout/stderr are collected, and success is decided by the exit code. Chat execution persists the native session id per "channel × role" and continues each turn with the corresponding CLI's create/resume arguments; different channels or different roles never share a session. Executions of the same session are serialized to avoid interleaved parallel turns. Templates are always used through `DEFAULT_COMMANDS` and do not accept overrides from Backend data.

Each tool's static declaration (detected executable name, command template, capabilities, model list, fallback effort levels, upgrade channel, ACP special cases) is split by tool into the `runtime/clis/` subpackage, one module per tool (`clis/grok.py`, `clis/kimi.py`…); `adapters.py` aggregates the declarations into the registries `DEFAULT_COMMANDS`, `ACP_SERVE_COMMANDS`, `KNOWN_CLIS`, `KNOWN_MODELS`, `EFFORT_SUPPORT`, and `UPDATE_SPECS`. To add a tool, add a declaration module and append it to `clis.SPECS`; the executors do not need to change. Execution behavior is still handled by the unified `CliAdapter`/`AcpAdapter`; for tools with native providers (claude/codex/pi), execution and effort levels live in their respective provider classes.

Tool-specific behavior travels with the declaration through optional `CliSpec` hooks, and `adapters.py` only dispatches: `session_args` (each CLI's create/resume argument syntax), `apply_permissions` (translating the unified file system permissions into native arguments, such as codex's `--sandbox` levels and the read-only→plan mode of claude/codebuddy), `prepare_env` (opencode's `OPENCODE_CONFIG_CONTENT` directory authorization injection), `parse_model_efforts` (parsing grok's `_meta.reasoningEfforts` vendor extension; the ACP protocol layer only passes the models block through), `parse_prompt_usage` (private vendor usage in the `session/prompt` response, such as grok's `_meta.usage` and trae's cumulative totals), `locate_binary`/`configured_models`/`update_plan` (the trio for pi's vendored installation; tools that declare `locate_binary` are treated as platform-managed installations, and at service startup `binary_path` is relocated according to the current data directory, so the database does not need manual edits after the data directory is moved), `account_usage_probe` (the account limit probing entry point for grok/kimi; the implementation is still in `usage.py`), and `latest_version` (a latest-version source other than npm, such as trae parsing `traecli update check`). The only tool-related code still in the executor layer is streaming output parsing (claude stream-json, codex stderr progress, opencode/cursor structured output extraction); it is coupled with the read loop of `CliAdapter` and can be split out only after a separate parser interface is designed.

Template placeholders (`render_command`):

- `{prompt}` — the fully assembled prompt (role positioning, project context, the recent conversation and trigger message in JSON format, paths of channel history files to read on demand);
- `{model}` — the role's fixed model; when empty, the token is removed together with the adjacent `--model`/`-m` flag, which explicitly uses the CLI default model;
- `{effort}` — the role's fixed reasoning effort (see the Effort section below); when empty, it is removed together with the adjacent `--effort`/`--reasoning-effort`/`-c`/`--config` flag;
- `{documents_dir}` — compatibility placeholder for the project document library path; new templates should use `{allowed_dirs}`;
- `{allowed_dirs}` — all local resource directories of the current project plus the document library; expands to repeated `--add-dir <path>`;
- `{workdir}` — the main working directory for this execution, for CLIs that need an explicit working root argument.

Print templates always include each CLI's non-interactive arguments, so headless execution never blocks on a terminal confirmation prompt. Copilot and CodeBuddy receive the extra directories one by one; OpenCode injects exact directory rules through `OPENCODE_CONFIG_CONTENT.permission.external_directory` and explicitly sets `read` / `edit` to `allow` for the project resources MissionCrew has authorized, preventing its built-in `.env` read prompt from being automatically denied in headless mode. The shared context also explains how to recover after a hard path denial: only go back to an authorized root and use an exact path; document resource URLs map directly to `MISSIONCREW_DOCUMENTS_DIR`; never switch to recursively searching a common parent directory. If OpenCode still stops at `tool-calls` because of a permission request, the failure summary lists this turn's authorized roots and the same recovery advice, so the orchestrator can fix the material location or re-dispatch; the platform does not retry automatically, to avoid repeating external write operations that have already completed. OpenCode also explicitly receives the main working directory and uses `--format json --thinking`, mapping completed reasoning blocks, tool calls/results, and step boundaries to run process events. The OpenCode CLI does not provide per-token deltas for this content, so what is shown here is stage-level progress. Cursor print mode includes `--force`. Claude/Codex always use their own native bidirectional providers. The tail of the diagnostic output is written to `.missioncrew/runtime/last-output-<adapter>.log` in the separate harness workspace for later review, so no logs are generated in the business code repository; channel messages store the complete final reply returned by the runtime, and very long content is only visually collapsed in the web UI.

### ACP stdio (`AcpAdapter`, Grok / kimi / kiro / qoder / trae)

These CLIs do not accept being invoked with "the prompt passed on the command line"; instead they run as a JSON-RPC 2.0 service on stdio (newline-delimited). The fixed serve commands are defined in `ACP_SERVE_COMMANDS`; Grok is started as `grok agent stdio`, with `--cwd` pinning the project working directory; Kimi and Qoder receive the project's extra directories one by one before the ACP service starts; Trae declares `sessionCapabilities.additionalDirectories` in `initialize`, so its extra directories are passed in the `additionalDirectories` of `session/new`/`session/load` instead (since traecli 0.209 the top-level `--add-dir` has no effect on `acp serve`); the list takes effect only when the session is set up, so when it changes the long-lived process is restarted under the new signature and the session is loaded again; Kiro uses its trust-all-tools mode, with external access handled by answering ACP permission requests. Protocol flow (`acp.py`):

```text
initialize → session/new|session/load → [session/set_model] → session/prompt
```

- The reply text comes from `agent_message_chunk` in `session/update` notifications and is concatenated into the final output;
- Usage: `usage_update` notifications only record the latest context state (even when they arrive outside a turn they do not enter the self-wake buffer), and at the end of the turn they are normalized together with the `usage` of the `session/prompt` response into one `usage/v1` event (see the usage events paragraph);
- Notifications before the `session/load` response are history replay (Kimi does not necessarily include the `isReplay` marker) and are used only for the runtime to restore context; they are not written into the current run's body, thinking, tools, or background wake events. After the load success/failure response is received, live notifications resume in protocol message order, and a failed or timed-out write also lifts the isolation. Notifications explicitly marked `isReplay` are always filtered out;
- `session/request_permission` requests sent back by the agent must be answered; otherwise the agent blocks until its internal timeout and the task appears hung. The platform runs headless and automatically picks a safe option from those the agent offers: allow once > allow for the session > reject once; when none is available, it returns a protocol error (it cannot reply cancelled, which would cancel the whole turn);
- Other unknown agent→client requests get an empty result, to avoid blocking;
- The whole turn shares one deadline, and on process EOF all waiters fail immediately instead of hanging.

ACP v1 defines the `session/prompt` response as the terminal boundary of a complete prompt turn: the agent may respond only when there are no pending tool calls, and residual updates after a cancel must also be sent before the response; the protocol has no unified lifecycle for "the response has returned, but a detached task is still running in the background and later starts a new turn automatically". Kimi currently attaches `rawInput.run_in_background=true` in the open fields of standard tool events and returns `task_id`, `status: running`, and `automatic_notification` in `rawOutput`. When MissionCrew recognizes this extended form, it registers a background task; if the task is still running when an intermediate `session/prompt` response arrives, the platform keeps the original chat run, ACP session lock, and event receiver valid, and starts an internal continuation turn in the same native session, asking the runtime to use its own blocking wait tool to consume the task's terminal state and final result. Other ACP runtimes that expose the same open fields can reuse this compatibility path; when they do not, the detached lifecycle cannot be inferred from ACP v1, and the standard `session/prompt` response remains the completion boundary.

The continuation mechanism above serves "short background tasks that finish within the turn"; long background tasks go through client terminals plus self-wake. MissionCrew declares `clientCapabilities.terminal=true` in `initialize` and implements `terminal/create|output|wait_for_exit|kill|release` (`_ClientTerminal`): the agent hands commands to the client to execute, **the process is owned by MissionCrew**, and its exit time is therefore visible to the platform; when output exceeds the limit, it is truncated from the head as the ACP convention specifies. In testing, Grok accordingly puts `background=true` commands into a client terminal and ends the turn immediately (the blocking `wait_for_exit` is answered asynchronously by the client after the process exits, without occupying the protocol reader thread); after the terminal exits, Grok spontaneously runs a reporting round outside any turn through its own extension (`_x.ai/task_completed` + an injected synthetic user message). The platform buffers `session/update` messages that arrive outside a turn into the wake pipeline: once the spontaneous turn is judged to have ended by a quiet interval (3s), they are handed together with the triggering task information through `RuntimeManager.set_wake_handler` to ChatEngine, which materializes them as a new run in the channel (the same pipeline as wake-ups for Claude background commands, but ACP has no reliable turn start, so it still delivers everything as a whole after the turn ends, and there is no Agent Tool token within the spontaneous reporting turn); when a new run's turn starts, any undispatched buffer is delivered first, so spontaneous reports do not get mixed into other runs. The kimi/trae binaries also contain terminal/* implementations; their behavior is to be verified once quota is restored. Long-lived sessions with live client terminals do not take part in idle reclamation (closing the client would also kill the terminal processes), and the instance snapshot reports the number of terminals as `background_tasks`; service exit still terminates all terminals, consistent with how Claude background commands are handled.

In chat scenarios, the ACP serve process and `sessionId` for the same "channel × role" stay resident and are reused within the MissionCrew server process; they are reclaimed after 30 minutes idle. After MissionCrew restarts or the process exits, the platform reads the session id from SQLite and calls `session/load` only when `initialize.agentCapabilities.loadSession=true`. Grok's load request additionally passes `_meta.noReplay=true`, because MissionCrew already holds the channel history and Grok's saved old `session/update` messages should not be replayed into the current run; as a defense, the receiving side also discards history notifications with `_meta.isReplay=true`. When the runtime does not support resuming or cannot resume, the platform explicitly degrades to `session/new` and adds the formatted recent conversation back into the first input of the new session.

### Agent Tool, Common Context, and Compaction

The chat prompt has two parts: the MissionCrew shared context and this turn's task input. All prompts for roles (shared context, turn input, injected banners, `manual.md`, the workspace README, Agent Tool action descriptions, and config-page chat instructions) are written in English; the language of human-visible content (final replies, messages, documents, task briefs) is set to Simplified Chinese by the single `Language` line in the identity section, while the notifications, error messages, and tool receipt summaries that the platform posts to channels remain in Chinese. The shared context is ordered as "what is read first is given first": the identity line (role, channel and its id, project and description, absolute path of the working directory, code repositories, language convention) → "How to Work" (one five-step flow each for executors and the orchestrator, with rules attached to the steps) → how to call the Agent Tool and the available actions → "Must Follow" (readable/writable directories, boundaries, handling of path failures, citation rules, read-only task snapshots, keeping the workspace out of business repositories, skill sources) → "Project Materials" (charter, development guidelines, guideline and skill index) → "Workspace Overview" (the root directory once, relative names of child items and environment variables, pointer to the manual) → the orchestrator-only "Orchestrator Duties" (discipline, querying on demand, collaboration chain budget) and "Project Inventory". This turn's task input marks the trigger type (human message, executor report, orchestrator dispatch, automation) with "This Turn's Trigger", then gives the trigger message JSON; for roles that can call `message.publish`, each turn is also prefixed with a "How Your Reply Is Delivered" section reminding them that the final reply is published automatically and should not be published again separately. The shared context states clearly that MissionCrew is an agent harness rather than a business code repository and explains that harness files never enter business source code. The common block carries a content-hash version and a compaction hint, asking the runtime to compact only ordinary conversation, tool processes, and task details and to keep the latest common block intact. Changes to project or role settings change the version; the bodies of guidelines and skills do not go into the prompt and do not count toward the shared context hash, so a body edit only adds a "Resource Updates" note to the next turn's input (listing the modified guidelines/skills and asking for them to be re-read) and does not trigger a full resend, while changes to index information such as name/description still change the version. A version received later replaces the old version entirely. The shared context is organized for progressive disclosure: the prompt keeps only the rules that must be followed at all times, while the usage of the platform's actions, the format conventions for dashboards/data sources/guidelines/skills/automations, and the details of the file system boundary are written in the workspace's `manual.md` (environment variable `MISSIONCREW_MANUAL`, re-rendered every turn) for agents to read on demand. The role roster, code repositories, dashboards, data sources, and automation list visible to the orchestrator are appended to the end of the common block as "Project Inventory" but do not count toward the hash; channels are listed by active id only, and details and archived channels are queried on demand through the `channel.list` action. The session saves the entry versions it last saw, and when entries are added, updated, archived, or disabled, only the differences are listed in the next turn's input, without triggering a full resend.

The common block is not resent every turn. A full injection happens only on: a new session or a resume degradation (with the recent conversation attached), a version change (with a note that it replaces the old version), or a reinjection trigger (with a refresh note). All other reused turns are incremental turns that send only a version reference header and this turn's task input. There are two kinds of reinjection triggers: Claude's `compact_boundary`/`microcompact_boundary` events and the Codex app-server's `thread/compacted` notification immediately persist a compaction marker; for runtimes without a compaction signal (ACP, the remaining print-mode tools), a fallback counts the cumulative input/output bytes and the number of incremental turns, and forces a full reinjection after roughly 500k bytes or 20 turns by default; `MISSIONCREW_CONTEXT_REINJECT_BYTES` / `MISSIONCREW_CONTEXT_REINJECT_TURNS` can override these (<=0 disables the corresponding trigger). The injection mode of each turn (full/incremental and the reason) is reported as a status event, making it easy to check what was actually sent.

The Agent Tool common block lists the current role's action scope and injects `MISSIONCREW_AGENT_TOOL_URL`, `MISSIONCREW_AGENT_TOKEN_FILE`, and `MISSIONCREW_AGENT_TOOL_PYTHON`. Runs of the same `channel × role` acquire the execution lock serially; the platform then atomically writes a capability bound to that run at the stable token path, the CLI does not submit a `run_id`, and the API determines ownership from the authenticated token. When a run ends, its token is revoked and the file deleted; the self-wake reporting turn of a Claude background command is materialized as a run through the `begin` callback at its start and gets a newly issued token, so write operations within that turn are authenticated the same way as in a regular run. Structured tool errors can be handled within the current agent turn, whereas text blocks in the final reply can only be parsed after the turn ends, so historical text blocks are kept only for compatibility reading.

The recent conversation JSON enters only the first turn of a new or resume-degraded session; normal resumes do not replay it again. The full channel history, documents, guidelines, skills, and tasks each live under `MISSIONCREW_WORKSPACE`, with corresponding environment variables. When chat roles create, modify, move, or delete documents or tasks, they use `document.publish`, `document.rename`, `document.delete`, `task.create`, `task.update`, `task.brief`, or `task.delete`; post-execution scanning of documents exists only for migration compatibility, and task snapshots are never synced back.

### Mock (`MockAdapter`)

A deterministic simulated runtime for running through channel collaboration at zero cost: when a trigger message contains "请 @某角色" ("please @some-role"), the simulated orchestrator, like a real runtime, executes the explicit command `message.publish` (with the `mentions` parameter) to dispatch collaboration, while `@roleID` in the reply body is just plain text. The platform accepts only this explicit dispatch channel, and non-orchestrators may mention only the orchestrator, so their mentions of other roles are denied by permissions; when a human selects a single role, it runs directly and the result stays only in the channel; when a human selects multiple roles, only the orchestrator is started and the original list is kept for it to coordinate; execution results dispatched by the orchestrator automatically return to the orchestrator. Test and demo seed data use it.

## Detection and Registration

- **Detection** (`detect_report`): probes PATH with `which` for each entry in the detection table, and for installed ones runs `--version` to extract a semantic version number (if no semantic version can be matched in the output, it is left empty, since some installation shims print unrelated hint text); pi is the exception: only the platform's vendored installation (`MC_HOME/pi/vendor`) is recognized, and the system PATH is not probed;
- **Registration** (`detect_backends`): one registration record per tool, storing the binary path, version, and default capabilities/tier/cost, and refreshing the tool's built-in model list: preset from `KNOWN_MODELS` (currently only claude: `""` (CLI default)/haiku/sonnet/opus/fable), while tools that declare the `configured_models` hook (pi) read it dynamically from the platform's `models.json`;
- The runtime management page shows only tools, versions, and installation status; each record has an enable switch, a disabled runtime cannot be bound to a role (saving returns 400), and executions of roles already bound to it explicitly report "不可用" (unavailable).

## Temporarily Enabling and Disabling Roles

A project role's `enabled` switch controls only new execution entry points: once it is disabled, the chat role bar and the mention picker no longer offer that role, and web structured mentions, CLI `@[role]`, orchestrator `message.publish`, and orchestrator dispatch for tasks are all rejected or skipped on the server side. Disabling does not delete the role configuration, message history, Agent Tool identity, or persistent runtime sessions, and does not interrupt turns that have already been accepted; after re-enabling, the original context can still be reused. To ensure the project always has a scheduling entry point, the current `orchestrator_role_id` cannot be disabled directly; you must first switch to another enabled role.

Enabled/disabled state belongs only to the human control plane. The project role roster in the orchestrator prompt does not list disabled roles; the Agent Tool returns `role_not_found` for both disabled and unknown roles, without exposing the "role disabled" state to agents.

Both the role editor and the global role template editor provide an "账户用量联动" (Account Usage Linkage) switch, with an explicit hint that it should stay off for third-party LLM APIs. Account usage linkage can bypass the control-plane restriction that "the current orchestrator cannot be disabled manually", because once quota is exhausted that orchestrator cannot keep executing either. Automatic disabling still only blocks new turns and does not interrupt executions already accepted; the page uses "用量联动" (usage linkage), "用量停用" (disabled by usage), and the estimated recovery time to distinguish the configuration from the current state.

## Model Lists

The model dropdown in the role editor merges two sources:

1. **The tool's built-in list** (`Backend.models`): an ordered list of model names only, with `""` meaning the CLI default and placed first. It is refreshed from `KNOWN_MODELS` at detection; pi instead reads it from the platform's `models.json` and refreshes it after `PUT /api/model-providers`; neither is **editable**: `POST /api/backends` does not accept a `models` field. The platform does not track the tier or cost of individual models, and quota is always deducted by the tool-level `cost_per_run`.
2. **Runtime dynamic discovery** (`list_runtime_models`, cached on the server for 10 minutes and likewise reused within the page for only 10 minutes; the ↻ next to the model dropdown in the role editor forces a re-probe through `GET /api/backends/{id}/models?refresh=true`, and the server cache is invalidated when the tool is updated or re-detection finds a changed binary/version. A tool's own model catalog can also change without a CLI upgrade; for example, grok refreshes `~/.grok/models_cache.json` from xAI when it renews online, and new models only enter the dropdown after a re-probe):
   - codex: by default reads the catalog available to the current account page by page through `model/list` of `codex app-server`; if the protocol fails to start, falls back to `codex debug models --bundled`;
   - antigravity: `agy models` returns tab-separated model slugs and display names, and the platform keeps only the slug; execution uses `--model`, and an empty value keeps the CLI default;
   - opencode: `opencode models` (a line-based `provider/model` catalog, with log noise lines filtered out);
   - ACP tools: a one-off session that parses the model catalog from the `session/new` response. The kimi/trae form is the select options with `category=model` in `configOptions`; the form that provides only `models.availableModels` (a `{modelId,...}` list, including `currentModelId`, aligned with Multica's parsing, as in older traecli versions) also supports `available_models`/`available` and bare arrays; when both are present, `configOptions` wins: the models block of traecli 0.209 holds combined "model/level" ids such as `glm-5.3/high`, which are not separately selectable models. Grok does not read the expiry of local credentials; if the first probe is empty or returns only the known single-model fallback `grok-4.5`, the CLI is restarted independently and probed once more, and the second result is used directly whether or not it is still 4.5, with no endless retries;
   - claude: the CLI has no enumeration command (`claude` has no `models` subcommand, and passing a wrong value to `--model` does not enumerate either), so the static catalog `CLAUDE_MODEL_CATALOG` is returned. It lists only concrete models accepted by `--model`, ordered by family and recency; stable aliases are in the tool's built-in list and do not appear again in this group;
   - mock: returns the tool's built-in list.

When saving a role, the model must belong to one of the two lists; an empty model = explicitly using the CLI default, which is always valid. At execution time the model is applied to this execution's configuration and is **not written back to the registry**: the registry always keeps tool-level entries.

### Custom Model Integration

Beyond the two tool-determined lists above, users can also integrate **any OpenAI / Anthropic-compatible API endpoint** (self-hosted inference services, gateway proxies, third-party hosting). This is a capability the platform commits to externally, independent of "who executes it". The "自定义模型接入" (Custom Model Integration) area on the global settings page handles adding, editing, and deleting; an integration entry contains an integration name, API protocol, Base URL, API Key, and a list of model ids. Once integrated, models enter the role's model list in the form `integration name/model id`.

The external contract is `GET/PUT /api/model-providers`:

- **Keys are never sent back to the browser**: for a literal apiKey, GET returns an empty string and sets `apiKeySaved=true`; only `$ENV_VAR` references are returned as is (a reference, not a key); in a PUT, an empty apiKey for a provider keeps the saved value, so the editing UI never needs to read out the plaintext and write it back.
- **Fields not shown are preserved**: PUT overwrites each provider as a whole, and before submitting, the page merges back the existing extra configuration (provider-level `compat`, model-level `contextWindow`/`cost`, and so on), so fields the UI does not expose are not wiped.
- **Writing refreshes immediately**: the structure is validated, the configuration file is tightened to `0600`, and the execution runtime's list of execution units is refreshed; `executor` in the response indicates whether that runtime is installed and enabled, and the page uses it to prompt the user to install or enable it first.

These models are currently executed by pi, and the configuration lives in its `models.json` (see the pi section above). The execution runtime is determined solely by `CUSTOM_MODEL_RUNTIME` in `missioncrew/api/backends.py`; switching it requires no changes to the external interface or the page.

## Effort (Reasoning Effort)

Some tools support specifying the reasoning effort per execution. Effort levels have two sources: **per-model** levels self-reported by the tool take priority, and when those are unavailable, the static fallback levels declared by each provider are used. Static declarations travel with the provider (`RuntimeProvider.effort_catalog()`): claude/codex/pi/antigravity declare them in their own provider classes, and the adapters handled by the built-in CLI/ACP executors (grok, copilot, kimi, mock) are centralized in `adapters.EFFORT_SUPPORT`; `RuntimeManager.effort_catalog()` merges all declarations into the full catalog used by `/api/traits`, and registering a custom provider takes over the effort levels of the corresponding adapter:

- claude: native `--effort` flag, levels low/medium/high/xhigh/max;
- codex: native `turn/start.effort`, levels minimal/low/medium/high/xhigh/max/ultra (a given model may not support every level; when a level is out of range, the app-server reports the error itself and it flows back to the channel as usual);
- grok: `grok agent --reasoning-effort` on the ACP serve command, static fallback levels low/medium/high/xhigh, with the actual levels discovered dynamically per model (see below);
- copilot: `--effort` on the ACP serve command, levels none/minimal/low/medium/high/xhigh/max (the model catalog does not self-report per-model levels, and copilot itself ignores the level on models that do not support it);
- kimi: no command-line level; uses the ACP-standard session config option instead: the `thinking` option with category=`thought_level` in the `configOptions` of the `session/new`/`session/load` response, switched within the live session through `session/set_config_option` before each prompt, so changing the level does not restart the long-lived process; static fallback levels low/high/max (K3), with the actual levels discovered dynamically per model (the K2.7 series has only on/high, see below); for an out-of-range level kimi reports an error (`-32602 Unknown thinking value`), which flows back to the channel as a failure of this turn;
- trae: uses the session config option like kimi, with option id `reasoning_effort`; no static fallback levels are declared, and all levels are discovered per model (most models have low/high/xhigh, GLM-5.2 has only high/xhigh; models such as Doubao-Seed-Code, MiniMax, and MiMo have no such option, so the dropdown is disabled), and no effort is offered when the model is blank (CLI default); for an out-of-range level trae reports `-32602 Unsupported reasoning effort for selected model`, which flows back to the channel as a failure of this turn;
- antigravity: native `--effort`, levels low/medium/high;
- pi: mapped to the thinking level (`--thinking`/`set_thinking_level`), levels off/minimal/low/medium/high/xhigh;
- mock: low/medium/high, only for exercising the pipeline in tests/demos;
- Other tools are not supported: the effort dropdown in the role editor is disabled, and the API returns 400 directly for a non-empty effort.

Like the model, effort is part of the execution combination fixed when the role is defined: an empty value = the CLI default, which is always valid; in print-mode execution it is injected through the `{effort}` placeholder of the built-in command template and, when empty, removed together with the adjacent flag. ACP tools use one of two approaches: those whose serve command template contains `{effort}` (grok/copilot) inject it with the command, and the protocol layer does not set it again; for those whose template does not (kimi/trae), `AcpAdapter.run` passes it to `acp.run_prompt(effort=…)`, and the protocol layer switches the level when the session self-reports a thought_level config option; if the session does not, it reports an "effort 未生效" (effort not applied) status instead of silently swallowing it.

### Discovering Effort Levels Dynamically per Model

Different models of the same tool support different levels: grok-4.6 has low/medium/high/xhigh, while grok-4.5 has only low/medium/high. Effort levels therefore cannot simply be hardcoded per adapter.

ACP tools self-report per-model levels in two ways, and `acp.list_model_catalog()` retrieves both together with the model catalog **in the same probe**: the level table is a by-product of the model catalog and needs no extra process. grok self-reports `supportsReasoningEffort` and `reasoningEfforts` in `models.availableModels[]._meta` of the `session/new` response (a private vendor extension, parsed by the `parse_model_efforts` hook in `clis/grok.py`); kimi uses the ACP-standard `configOptions`, but `session/new` gives only the `thinking` values of the **current model**, and those values vary by model (K3/K3-256k have low/high/max, the K2.7 series has on/high), so within the same probe session the protocol layer calls `session/set_config_option(model)` for each model and reads that model's levels back from the `configOptions` in the response, with no tool hook needed; trae's `reasoning_effort` works the same way, and models without that option stay out of the table. Further up the chain come `adapters.list_runtime_model_catalog()` (normalized from low to high by `EFFORT_ORDER`, since grok itself returns them from high to low), then `RuntimeManager.list_model_catalog()`, and finally `ApiContext.discovered_catalog()`, which caches the levels together with the model catalog for 10 minutes.

`RuntimeManager.effort_options(backend, model, model_efforts)` decides the final list: if the given model has levels in the self-reported table, those are used; otherwise it falls back through `provider_for()` to the static levels declared by that Backend's provider. A blank model (the CLI default model) also takes the fallback, because in that case it is unknown which model the CLI will end up choosing. The self-reported table is passed in by the caller (the API uses the cache, the CLI looks it up live); this function itself does not probe the runtime.

The effort dropdown in the role editor takes per-model levels from the `efforts` field of `/api/backends/<id>/models` and recalculates when the model changes; if the role's saved level is not in the new model's list, it is kept and marked "该模型不支持" (not supported by this model), rather than silently rewriting a value the user configured.

This layer of validation is necessary because **`grok agent` does not validate effort levels**: unlike codex (where the app-server reports an error that flows back to the channel), grok does not report an error for an out-of-range level but silently falls back to the model's default level (in testing, xhigh + grok-4.5 fell back to high). If it slipped through, the user would see no hint at all in the channel, so it can only be blocked when saving the role, based on the selected model.

For grok/copilot the effort goes into the ACP serve command, so changing the level changes the client signature in `acp.py`, and the long-lived session restarts the process with the new command instead of keeping the old level. The kimi/trae level is not in the command; it is overridden by `set_config_option` before each prompt and switched directly in the live session. As with the model, when effort is changed back to empty (CLI default), it is no longer sent, and the session keeps the last level set until the process is reclaimed.

## Upgrades

`UPDATE_SPECS` declares the upgrade channels for each tool, and `update_plan` chooses one based on the installation method:

- **npm-managed first**: a binary is considered npm-managed only if its realpath lies under `node_modules/`; in that case checking (querying `latest` in the npm registry) and updating (`npm install -g <pkg>@latest`) go through the same channel, which prevents the self-updater from installing the new version elsewhere while the old copy in npm keeps occupying PATH;
- **Non-npm installations** use the tool's own update subcommand (`claude update`, `opencode upgrade`, and so on), since the self-updater knows how it was installed;
- For kimi, both the current Kimi Code native build and the npm build look up the latest version from `@moonshot-ai/kimi-code`, not the PyPI version of the old Python `kimi-cli`; native installations run `kimi upgrade --yes`, skipping the confirmation prompt when the server has no interactive stdin, while npm installations are still updated by the npm-managed rule above.
- copilot is often managed by the VS Code extension, and no update is offered for non-npm installations; trae is installed by its native installer: the latest version comes from the `CliSpec.latest_version` hook parsing the text output of `traecli update check`, and updating runs `traecli update` (no confirmation prompt).

Constraints: update commands are a fixed allowlist and never concatenate user input; updates of the same runtime hold a mutex lock (concurrent requests get 409); while an update is in progress, no chat executions are dispatched to that runtime, so agents never run on a half-updated binary; version comparison only considers the numeric segments of semantic versions.

## Execution Environment

In the process environment of each execution, the working directory is still the channel workdir (the bound code repository, when one is bound), and the platform does not create `.missioncrew` in it. When the channel's bound directory no longer exists (for example, a task worktree has been cleaned up), assembly does not recreate it but falls back to the default directory `channels/<channel id>` inside the platform data root, with a notice in the shared context and in the orchestrator's channel roster; to continue working in the original directory, recreate the directory first or create a new channel. `MISSIONCREW_WORKSPACE` points to the harness of the current channel×role inside the platform data root, which centrally holds project materials, task snapshots, role-isolated history, tokens, and runtime diagnostics. Agents publish documents, edit tasks, and append status briefs through the Agent Tool; task snapshots are read-only and are not synced back after execution. A runtime may access only the directories explicitly listed in the prompt and should not use `/tmp`, `/var/tmp`, or other unauthorized paths; temporary files go in the directory conventionally used by the business repository or in `$MISSIONCREW_WORKSPACE/temp`. Agent executions in a channel have no time limit; they run until the runtime returns, fails, or the user actively stops them.

As for environment variables, the child process environment is the result of `host_isolated_environ()` overlaid with this execution's `cfg.env` (the `MISSIONCREW_*` variables injected by the platform). Otherwise the service process's environment would be passed whole to the Agent CLI, and variables injected by the host make the child process believe it is running inside that host: the CLI connects to the host's IPC, and `git` calls the host's askpass and hangs in headless execution. `runtime/base.py` therefore strips a set of variables on the basis that "the variable comes from the host": prefixes such as `VSCODE_*`, `CLAUDE_*`, `CURSOR_*`, and `TERM_PROGRAM*`, plus specific variables whose names do not reveal their origin: `CLAUDECODE` (no underscore, so prefix matching misses it), `GIT_ASKPASS`, `SSH_ASKPASS`, `GIT_EDITOR`, `PYTHONSTARTUP`, `SSH_AUTH_SOCK`, `SSH_CLIENT`, and `SSH_CONNECTION`.

**PATH and proxy settings (`HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY`) are not stripped**: PATH is not a source of contamination, and the service also relies on it to detect which CLIs are installed on the machine, so rebuilding a minimal PATH in the startup script would cause tools installed in non-standard directories to be misjudged as not installed; stripping proxy settings would make agent downloads fall back to direct connections. Stripping happens at the dispatch layer rather than in the startup script, so agents get the same environment whether the service is started by pm2, the CLI, or tests; to block a new variable, just edit that list in `base.py`.

For the full directory responsibilities, history isolation, and internal data boundaries, see [Agent harness workspace and project material boundaries](agent-harness-workspace.md).

## Integrating a New Tool

1. Implement `start`, `stop`, `capabilities`, and `list_models` of `RuntimeProvider`, and register it through `runtime_manager.register(adapter, provider)`. Long-lived providers should also implement `shutdown`. If account limits are supported, set `capabilities().account_usage=true` and implement `account_usage()`; the provider must return a unified snapshot and must not put credentials, user identity, or upstream error bodies into `message`. The business layer adds no adapter-conditional branches.
2. If you reuse the built-in print-mode or ACP executor, add the command template, session arguments, and permission translation only inside the runtime package; raw executors are not exported to the main program.
3. Add binary discovery, the model catalog, and the upgrade strategy inside the runtime manager; models, effort, and capabilities are all exposed through the unified query interfaces.
4. Bidirectional protocols always emit process events through `ExecutionConfig.emit` and request permissions or user input through `ExecutionConfig.interact`; providers must not depend directly on the Store, FastAPI, or web data structures.
5. Add contract tests for the provider, and keep the architecture boundary test that "nothing outside `missioncrew/runtime` may import raw executors". Account limit tests use sanitized fixtures and deterministic protocol processes and must not depend on real accounts or live quotas.
6. Runtime start commands belong to the provider implementation and do not go into the Backend data model; when adding a tool, also implement the fixed command, permission translation, session reuse, and the corresponding tests.
